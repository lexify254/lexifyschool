# Lexify School — Implementation Plan

## Scope and architecture

Build the role-based Lexify School platform in the existing Next.js project, using the user's latest instruction as the scope authority: **all on-site payment processing is excluded**. Tutoring, Academy, and project-store prices are informational listing details. A booking or purchase-intent button opens a WhatsApp chat with the relevant seller and an item-specific prefilled message. Each internal handoff records an aggregate outbound-click event; the platform cannot determine whether a WhatsApp message is sent or received, so metrics must be labelled as handoff clicks rather than people contacted or completed inquiries. A seller may manually issue a separate receipt only after confirming a sale arranged outside Lexify School. The receipt is seller-reported, not a Lexify-verified payment or tax invoice.

Use Next.js App Router, React, TypeScript and Tailwind, with the existing Supabase project `lexify school` (`ramwiruriaogrnaweabd`, `eu-west-1`) as the external source of truth for Auth, Postgres, Storage and Realtime. The WebDev Node server is enabled for Next rendering/API routes; the Manus-managed MySQL database remains disabled. Apply additive, reviewed Supabase migrations; do not reintroduce payment-provider tables or functions.

Use server-side Supabase clients for protected operations and browser clients only for public/authenticated interactive views. RLS must enforce data ownership and roles. Server routes own role checks, content administration, learning-data mutations, access-controlled downloads, PDF generation, inquiry-event logging, and receipt issuance/verification. Seller contact links use the existing normalized Kenyan WhatsApp URL builder; missing/invalid contact details fail closed with an explanatory message. Payment gateways, checkout, payment webhooks, refunds, commissions, transaction/payment status, payouts, and payment credentials remain out of scope. Email and malware-scanning adapters remain environment-configured and must never imply successful delivery when unavailable.

Curriculum remains data-driven: education systems, levels/status dates, learning areas, tracks, KCSE groups, subject relationships, rules, combinations, assessment scales and illustrations live in Supabase. Signup and curriculum management consume those records. A reusable accessible `SubjectCard` uses cached Lucide icons from stored `icon_name`/`accent_color` when there is no custom SVG/PNG illustration. Seed curriculum values are provisional and require official KICD/KNEC verification before institutional use.

## Project structure

- `src/app/`: Next.js App Router layouts and public, auth, role-portal, admin, Academy, project-store, receipt-verification and API routes.
- `src/components/`: responsive application shell, role navigation, reusable `SubjectCard`, signup forms, course/product/class cards, learning controls, WhatsApp handoff links and seller receipt forms.
- `src/lib/supabase/`: browser, server and privileged clients; session handling, role guards, storage and RLS-aware queries.
- `src/lib/curriculum/`: rule evaluation, subject-choice validation, assessment conversion and curriculum helpers shared by UI and server validation.
- `src/lib/whatsapp/`: validated seller contact normalization, item-specific `wa.me` destinations and minimal handoff tracking; no WhatsApp API or automated sending.
- `src/lib/pdf/`: branded learning reports, certificates and seller-issued receipt PDFs using the existing PDFKit/QRCode dependencies and supplied Lexify School seal.
- `src/lib/notifications/`, `src/lib/security/`: optional notification adapters, validation/rate limits and upload policies.
 - `supabase/migrations/`: application tables, indexes, triggers, RLS, storage policies, aggregate WhatsApp handoff events and seller receipt records; `supabase/seed.sql` and manual admin setup SQL hold editable curriculum and safe defaults.
 - `tests/`: curriculum, authorization, WhatsApp URL, receipt policy and core feature tests; no payment-provider tests.
 - Root configuration: `.env.example`, `Dockerfile`, `README.md`, `TODO.md`, `plan.md`, `app.config.ts` and `public/manus-routes.json`; self-hosted website visuals live in `public/` so Vercel does not depend on Manus Storage paths.

## Accounts, parent linking and teacher profiles

- Keep Supabase Auth as the identity/session source across the shared App Router shell. Navigation must not sign users out. Signed-in users see their current avatar near the upper-left of the shared header; clicking it opens the current role's workspace. Keep account settings at `/profile`; profile photo uploads must validate image type/size and write only to an owner-scoped storage path.
- Parent signup is parent-specific: ask for the parent's name, email/password and a student identifier to link to their child. Do not request grade, class, curriculum or student-only choices from a parent. Resolve the identifier server-side, create the parent–student relationship only for a valid eligible student, and never expose a child roster or student details to unaffiliated parents. Preserve guardian consent and the existing UUID/RLS ownership model.
- Student accounts must receive a durable, unique identifier that can be safely shared with a parent; display it on the student's profile. Do not use a child's email, full name or raw Auth UUID as the public lookup value.
- Teacher profiles support several active curriculum-linked subjects, selected service offerings (including tuition), informational pricing and teacher-managed learning materials. Store subjects through the existing teacher-subject relation; enforce ownership on profile/material changes and retain private or access-controlled storage for classroom files. Do not invent teacher identities, service details, prices or published classes.
- Teacher search remains server-side and URL-driven. Provide a polished icon-led query field, clearly grouped filters and an explicit sort selector, with accessible labels/focus and useful mobile layout; do not fabricate marketplace results.

## Design direction

- **Design Movement:** modern Kenyan digital-school editorial, combining a dependable learning platform with the friendly clarity of a contemporary education marketplace.
- **Core Principles:** trustworthy for parents; energetic but calm for teenagers; mobile-first and low-bandwidth; prices and WhatsApp handoffs are clear and honest.
- **Color Philosophy:** deep royal blue `#1E3A8A` communicates trust and focus; warm gold `#F59E0B` signals progress and action; white/light-gray surfaces preserve readability, with dark mode for community and dashboards.
- **Layout Paradigm:** compact mobile-first navigation, focused page headers, scannable stacked cards and clear portal side navigation on wide screens; keep the homepage editorial and catalogue pages filterable.
- **Signature Elements:** rounded subject cards with colored icon tiles; blue-to-gold progress accents; clear content-status and teacher-verification labels.
- **Interaction Philosophy:** minimize typing on mobile, explain disabled/invalid curriculum choices inline, make WhatsApp seller handoffs explicit, and never pretend an unavailable backend operation succeeded.
- **Animation:** brief opacity/position transitions and progress feedback only; respect reduced-motion settings and avoid decorative motion that costs bandwidth.
- **Typography System:** Inter for interface and body text with a bold geometric display treatment; large headlines, compact labels and highly legible form copy.
- **Brand Essence:** a dependable Kenyan learning hub connecting learners, guardians and teachers with curriculum-aligned tutoring and practical digital skills; **smart, supportive, credible**.
- **Brand Voice:** encouraging, direct and reassuring. Examples: “Learn at your pace. Grow with the right support.” / “Ask the seller about a class or course on WhatsApp.”
- **Wordmark & Logo:** show only the owner-supplied circular Lexify School seal in the shared header, browser icon and PDF receipt, with the outside background transparent; preserve the original asset. `app.config.ts` uses the durable HTTPS transparent derivative for platform branding.
- **Signature Brand Color:** deep royal blue `#1E3A8A`.

## WhatsApp handoff counts and seller receipts

- Replace any payment-count metric with two distinct records: aggregate outbound WhatsApp handoff clicks, and seller-issued receipt records. A click is not evidence of a sent message, a unique person, a completed sale, or payment. Do not store the clicker's name, phone number, message text, or raw IP; aggregate by listing and seller only.
- Public and authenticated WhatsApp actions route through a same-origin endpoint which validates the published item and seller, records the handoff event, and redirects to the validated `wa.me` destination. It must not accept arbitrary redirect hosts. If logging fails, preserve the seller handoff; if a contact is missing, do not create a misleading button.
- Teachers may issue receipts only for their own seller profile; administrators may issue platform receipts and view all records. Receipt creation is a manual seller action after the seller confirms the externally arranged sale; a handoff click never creates a receipt. Store a snapshot of seller, receipt number, issue date, item/description, quantity, unit price and total in KES, plus an optional buyer name. Do not store payment credentials, method, status, or processor identifiers.
- Generate a downloadable server-side A4 PDF with the existing Lexify School logo, receipt number, seller and item details, amount/date, and a QR code to a public verification page. The verification page exposes only the receipt number, seller, item, total and issue date—not buyer details—and states that it is seller-issued, not verified or processed by Lexify School, and is not a tax invoice. Only the owning seller and administrators may access full receipt data or download PDFs.
- Use the current Lexify dashboard and document styles; no new decorative assets are needed. Existing `pdfkit`, `qrcode`, and `public/lexify-mark.svg` are available. Build QR links from `NEXT_PUBLIC_SITE_URL` when configured, otherwise use the current published Lexify origin; never derive a public receipt URL from an internal Preview host. Update the environment value if the public domain changes.

## Interface polish and teacher verification

- Upgrade the public teacher, Academy, and Projects catalogues' GET search inputs to consistent, polished, icon-led search fields with visible keyboard focus, responsive sizing and clear labels. Keep their current server-side filtering, URL parameters, and no-JavaScript form submission behavior intact.
- Simplify signup to Supabase email/password with required email verification; remove SMS signup and ask only for necessary account details. No phone number is required to create student, parent or teacher accounts; teacher WhatsApp is optional. Provide accessible curriculum, grade and subject dropdowns for students and teachers, plus optional curriculum/subject preferences for parents. Keep live-catalogue validation and required student guardian consent; do not imply that an account was created until Supabase confirms signup or email verification.
- Add a restrained, accessible teacher-dashboard banner explaining truthfully that a verified badge may help a teacher reach more students. An eligible teacher can request verification, view the Admin-configured fee and a 14-calendar-day free-trial offer, and see pending/trial/expired/rejected states. Do not invent a fee: until Admin configures one, show a clear not-yet-configured state. The free trial starts only when Admin approves the request. The badge ends after the 14-day trial unless Admin manually confirms continuation; any fee arrangement happens outside Lexify, through the already configured WhatsApp handoff when available. Do not add checkout, card collection, automatic billing or payment-provider credentials.
- Provide administrators with a protected review queue and settings for the verification fee. Admin can approve/reject requests, start the 14-day trial, manually continue/revoke verification, and record the reviewer/time. Keep verification state and fee settings out of teacher-controlled writes; enforce roles in server code and Supabase RLS/RPCs.
- Confirm the protected Admin receipts page allows an administrator to manually issue and download the existing branded PDF receipt after attesting to a completed sale arranged outside Lexify School, in addition to reviewing seller-issued receipts. Preserve the no-payment boundary.
- Visiting `/admin` while signed out opens a simple email/password login. A first-time account is created through a signup link and must verify the designated owner's email before a one-time first-Admin claim can succeed. The claim stores `admin` against the verified Supabase Auth UUID; subsequent authorization uses the UUID and role, not the email string. Public signup must never offer Admin, and a verified email change must not silently remove an existing role.

Reuse Lucide icons and existing brand colors. Implement the signup backdrop and teacher banner with lightweight CSS rather than adding dependencies or decorative image assets. Banner motion is optional, brief, and disabled for `prefers-reduced-motion`.

## Serving and material constraints

Use the enabled WebDev Node server for Next.js preview and managed publication; the app must honor `PORT`. Keep the code Vercel-compatible and document deployment. Supabase Auth/Storage/Realtime and email/malware services are external and must use server-only secrets where appropriate. Do not include payment-provider keys or checkout routes. Keep `/manus-routes.json` synchronized with the implemented page routes. The `/admin` entry remains protected by the designated owner's verified Supabase Auth UUID and Admin role, never by a client-provided email/password shortcut; document the safe first-claim and subsequent sign-in path. The current project configuration has auto-publication enabled, so checkpoint pushes may publish; do not change this setting. Preserve the project's configured port, canonical repository and existing history.

## Current request — signup recovery, course materials, profile completeness and analytics

Continue the existing Next.js/Supabase architecture and preserve the current payment-free business boundary. Do not create fake users, courses, prices, progress or learning records.

- **Teacher signup recovery:** preserve email/password signup and email verification. Make teacher onboarding recoverable when a verified account exists but queued subject/profile writes fail; resume only through the authenticated account and clear pending metadata only after all required writes succeed. Give teachers a useful recovery path instead of directing them back to signup; preserve the same shared handling for students where applicable. Never present an account as fully ready before Auth/profile setup succeeds.
- **Profile completeness and parent details:** allow every role to update a private profile picture, short bio and other optional personal details through owner-authorized writes. Add a parent's own WhatsApp contact and keep the Auth email authoritative. Parent linking accepts the shareable student ID displayed in the student's profile; the request remains pending until the student confirms. No parent grade/class/curriculum fields. Keep learner PII and private avatars private; only teacher information deliberately needed by the public marketplace may be public.
- **Persistent navigation and avatar placement:** keep the Supabase user session when moving between Home and sections, only clearing it on explicit sign-out. Place the signed-in profile avatar at the upper-left side of the shared site header/landing page and route it to the signed-in role's workspace; keep account settings at `/profile` and use an accessible fallback when no photo exists.
- **Admin-managed courses and price:** extend the protected Course Manager to author new coding/computer-package courses, set informational prices in KES, manage draft/published state, and attach PDFs/documents/practice files to courses or lessons. No on-site checkout, collections or payment processing; seller handoffs and off-site receipt rules remain unchanged.
- **Subject-aligned revision library:** add an additive, private revision-material index tied to actual curriculum grade and subject records, with Admin publication/archive and access-controlled student discovery/download. Published materials should appear only for a student's selected, matching subject/grade; confirmed parents may view linked-child resources only within existing consent/RLS boundaries. Use private object storage, server-side ownership/role checks, short-lived authorized downloads, and explicit storage policies. Enforce a 100 MiB per-file cap and strict type/signature validation; per the user's later instruction, do not require or claim malware scanning.
- **Progress visualizations:** provide accessible charts for Admin, student, parent, teacher and guest views from recorded application data only. Student plots may use actual subject/date scores and attendance; parent plots must be limited to confirmed linked children; teacher plots must be limited to owned classes and existing attendance/assessment/submission records; guest plots may use that guest's real course lesson completions; Admin plots may aggregate real signups, course/lesson activity, assessment and attendance records with accurate labels. Preserve dimension/denominator differences, show honest empty states, and never synthesize missing data or mislabel clicks, courses, or activity as payments/sales.
- **Circular seal:** create a new transparent-background logo derivative by removing only background pixels connected to the outside of the seal, retaining white interior design details. Preserve the original asset; use the derivative consistently wherever the seal is presented and keep platform logo metadata on a durable HTTPS asset.

Use additive Supabase migrations and tests for new tables, pricing, RLS, storage policies and endpoints; verify teacher signup failure recovery and authorization without creating live test accounts or fabricated data. Uploads are capped at 100 MiB and use private storage plus file type/signature checks. Malware scanning is intentionally not configured or claimed, following the user's later instruction. The established project structure remains the same: `src/app` owns pages/APIs, `src/components` owns forms/dashboards, `src/lib` owns auth/security/data logic, and `supabase/migrations` owns additive schema and policy changes.
